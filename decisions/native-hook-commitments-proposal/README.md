# Proposed native issuance commitments

This directory is an inactive review artifact. It changes no contract, release input, runtime authority or approved requirement. All test identities and byte sequences are synthetic. No candidate digest is selected. Base: `e68b3ef6`.

The smallest acyclic design retains the constructor's existing two bytes32 equality checks. `bindingDigest` commits a predeployment binding document; `runtimeDigest` commits an external issuance runtime-authority document. The binding document includes the runtime commitment, so changing runtime evidence also changes the binding. A separate final release record binds the derived hook and pool. This supplements requirement 71's reproducible evidence semantics without treating arbitrary owner-chosen values as evidence.

The exact proposed formula is SHA-256 of `ASCII(domain) || 0x00 || UTF8(canonical(document))`. Domains are `HOOKEMON_NATIVE_ISSUANCE_BINDING_V1` and `HOOKEMON_NATIVE_ISSUANCE_RUNTIME_AUTHORITY_V1`. The result is lowercase 0x-prefixed bytes32. The existing Solidity guard only compares these values, so an ABI/Keccak wrapper adds no necessary property. This deliberately simplifies the earlier unapproved sketch, which suggested an ABI/Keccak envelope.

`commitments.mjs` is the executable proposal schema: exact object keys; recursively lexicographic key ordering; printable ASCII strings; unsigned integer values encoded as canonical decimal strings; no JSON numeric values in commitment documents; array order preserved; no trailing newline. Closure and authority arrays require canonical order and uniqueness. Compiler standard-input bytes are opaque committed bytes and may contain ordinary compiler numeric settings. Its source entries must contain embedded content matching retained source bytes; URL-only sources refuse. Compiler binary, standard input, all dependency sources, tool/config/lock inputs and their exact paths/hashes belong in the source closure. Complete compiler settings are covered by the exact standard-input bytes.

The helper verifies supplied bytes against every listed file hash and refuses missing or extra supplied files. It cannot establish that a caller supplied the complete production compiler/tool closure. The adopted release producer must construct that inventory from its actual hermetic build inputs and compare all compiler sources, imports and tool inputs; no dynamic imports or filesystem/network fallback may escape it. Source filenames need not be deployment addresses. The required requirements SHA must independently match the frozen requirements bytes.

External runtime records include role, address, code bytes, ABI bytes, observation bytes and exact block identity. This hashes the claimed evidence, not its truth. Existing release evidence validation must authenticate official provenance, finalized chain observation, actual code/ABI correspondence, proxy implementation where applicable, allowed authority semantics and all required provider roles before accepting the document. The synthetic fixture intentionally cannot pass that release validation.

The independent deployment inputs include graph factory, token/custody init-code hashes, and their effective CREATE2 salts. `tokenEffectiveSalt` and `custodyEffectiveSalt` mean the final provider-derived salts, not the applicant salts. The official provider derivation also binds the chain, router, graph factory, route namespace, graph nonce, target identifier and applicant salt. Its route namespace depends on the source-bundle content hash. The adoption check must therefore prove that the entire source bundle, not only the two init codes, excludes derived commitment documents, materialized hook outputs and final attestation. They may enter this document only after an independently reproduced dependency graph proves that neither init code contains the hook commitment, derived hook address, final pool ID, final release hash or another recursively dependent artifact. Hook-dependent custody configuration belongs in later atomic initialization and the final release record. If the actual provider graph does not permit this separation, this proposal cannot materialize that graph without revising the design. The pure helper does not claim to prove absence of indirect dependencies inside arbitrary byte strings.

The final release record, under existing release authority, must bind both commitment documents and hashes, exact hook constructor bytes, hook salt, init-code hash, derived hook address, materialized runtime hash, complete PoolKey/pool ID, independently derived token/custody addresses, graph calls, provider admission and finalized deployment observations. It is never hashed back into either constructor commitment. Full final source/build/deployment verification remains required. No provider approval follows from a hash or successful build-only preflight.

`requirements.patch` adds explicit semantics and tests to `REQ-provider-binding-3`; it does not activate revision 72. `architecture-proposal.json` lists the proposed machine-interface delta and adoption work. `REQ-provider-binding-1` already requires final provider/runtime binding and remains unchanged. The old text in `REQ-provider-binding-2` still describes the historical asset/vault arrangement; this proposal does not silently rewrite that unrelated native migration inconsistency. The coordinator must resolve its native authority text separately before freezing the release. `REQ-token-core-4` remains unchanged: official issuance compatibility still needs evidence.

Adoption requires an owner-approved revision, schema freeze, production helper integration, real source-closure inventory, independently authenticated runtime evidence, and final-release verification. It does not require changing the Solidity equality guard or economics. No helper is imported by active release code.

Verification: six focused Node tests passed. They cover canonical/domain vectors, reproducibility, direct self-reference rejection, byte/closure/runtime mismatches, every role/economic mutation and invalid canonical types. The envelope vector was independently calculated with Python hashlib. They prove hashing mechanics, not provider facts, a full production dependency closure or launch admission.

The retained read-only candidate currently inventories 14 source-bundle files, including unmaterialized compiler artifacts and a provider inspection record. That inventory contains no final hook constructor, commitment document or final attestation path. This is a property of that proposed inventory, not approval of its completeness or a guarantee about a future bundle. Any inventory or provider-derivation change invalidates the coordinate proof and requires recomputation before adoption.
