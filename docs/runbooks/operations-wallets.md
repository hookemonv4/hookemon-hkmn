# Operations Wallets Runbook

The Phase 3 money path uses exactly two bot identities. They are generated by the bot Mac and stay in that Mac's login Keychain; the owner does not need a hardware wallet for them.

- **Operations EVM** — `operations-evm`, stored under Keychain service `hookemon-operations` and account `operator-evm`.
- **Operations Solana** — `operations-solana`, stored under Keychain service `hookemon-operations` and account `operator-solana`.

`hookemon-wallet` manages those identities and their readiness. The wallets hold only the per-cycle 2.5 percent Operations budget after the onchain claim, subject to the onchain six-hour rolling claim cap (21600 seconds, owner decision 2026-09-04). The CLI does not authorize a process claim, bypass transaction policy, fund an account, sign an arbitrary request, broadcast a transaction, or deploy anything.

## Security boundary

The private material stays in the operating-system Keychain. The Node application, repository, cycle journal, dashboard, CI, shell history, chat, and environment variables must never receive a private key, seed, mnemonic, or exported Keychain secret.

For Operations wallets, do not use environment variables for secret material. Environment configuration may name public accounts or a signer backend, but it must not contain the wallet's private material. This rule is separate from the narrowly approved `PROGRAMMABLE_API_KEY` policy for read-only Programmable preflight work.

The CLI exposes public identity metadata and readiness only. It does not provide a secret-export command.

## Standing authority artifact

Production signing also requires an owner-signed standing-authority document, its owner and policy
public keys, and a private artifact at
`<stateDir>/standing-authority-step-authorizations.json`. The artifact is a regular non-symlink
file with mode `0600`, canonical JSON plus one newline, and schema
`hookemon.standing-authority-step-authorizations.v1`. It contains the verified authority digest and
an `entries` array of `{ signerRole, intent }` values; each intent is already policy-signed and
bound to that digest.

The runner opens the artifact without following links, verifies its private regular-file inode
through the open descriptor, and reads from that descriptor. A path replacement cannot supply
alternate artifact bytes after validation.

The resolver selects an entry only by the exact cycle ID, stage, authorization kind, request digest,
and signer role. The artifact contains neither a private key nor signing capability. A missing,
non-private, non-canonical, digest-mismatched, duplicate, or non-matching artifact entry refuses
the production signing boundary before the signer is reached.

Configure the authority document and public-key paths together through
`HOOKEMON_STANDING_AUTHORITY_PATH`, `HOOKEMON_STANDING_AUTHORITY_OWNER_PUBLIC_KEY_PATH`, and
`HOOKEMON_STANDING_AUTHORITY_POLICY_PUBLIC_KEY_PATH`. Do not place the artifact, private material,
or a policy signature in an environment variable. An expired first use is refused without a day-cap
or nonce reservation; a replay only reuses the exact decision already persisted before expiry.

For storage, the short-lived wallet child starts this executable with only `-i` in its process arguments:

```text
/usr/bin/security -i
```

It sends this exact command line to that process's standard input, with the generated secret replacing `<generated-secret>`:

```text
add-generic-password -a operator-evm -s hookemon-operations -w <generated-secret> /path/to/login.keychain-db
```

For an approved replacement, the child sends `add-generic-password -a operator-evm -s hookemon-operations -U -w <generated-secret> /path/to/login.keychain-db` instead. The Solana command uses `operator-solana` in the same position. The child obtains the absolute login-Keychain path from `security login-keychain`, verifies it is also the current default, and includes that public path explicitly so a later default-Keychain change cannot redirect the write. `security(1)` documents `-i` as interactive mode. This keeps the generated secret out of process arguments and shell history: it exists only in the short-lived child buffer and the child-to-`security` standard-input stream, then the child clears its known buffer. Never run a copied command with a real secret yourself.

## Create the two identities

From a repository checkout, run these exact commands on the owner-approved Mac:

```sh
node packages/adapters/bin/hookemon-wallet.mjs generate --identity operations-evm
node packages/adapters/bin/hookemon-wallet.mjs generate --identity operations-solana
```

When the package's command registry exposes `hookemon-wallet`, the shorter command is equivalent.

The complete generation grammar is:

```text
node packages/adapters/bin/hookemon-wallet.mjs generate --identity operations-evm|operations-solana [--service hookemon-operations] [--keychain-command /usr/bin/security] [--replace]
```

Generation reports only the public identity and its service/account metadata. It does not print private material. The defaults are the service and account names listed above; specify them only when an explicit operations record requires a different Keychain location.

Generation refuses to replace an existing identity unless `--replace` is present. With `--replace`, the CLI first prints one public JSON line containing `{ "replaced": ... }` for the current identity, then attempts the Keychain replacement and prints the new public JSON line. Preserve the first line before proceeding. Treat `--replace` as the final identity-creation step of a reviewed rotation, never as a convenience reset. It does not update onchain Operations authority, policy allowlists, cycle records, or funding destinations.

## Inspect and prove readiness

```sh
node packages/adapters/bin/hookemon-wallet.mjs show --identity operations-evm
node packages/adapters/bin/hookemon-wallet.mjs show --identity operations-solana

node packages/adapters/bin/hookemon-wallet.mjs probe --identity operations-evm
node packages/adapters/bin/hookemon-wallet.mjs probe --identity operations-solana
```

`show` returns the public identity and Keychain service/account labels. `probe` makes the short-lived child sign and verify a fixed internal test digest or transaction, then reports readiness. It never signs a requested money movement and never broadcasts.

The complete inspection grammar is:

```text
node packages/adapters/bin/hookemon-wallet.mjs show --identity operations-evm|operations-solana [--service hookemon-operations] [--keychain-command /usr/bin/security]
node packages/adapters/bin/hookemon-wallet.mjs probe --identity operations-evm|operations-solana [--service hookemon-operations] [--keychain-command /usr/bin/security]
```

Run both probes before enabling a signer service, after a Keychain access-policy change, and after recovery or rotation. A failed probe means the affected identity has not satisfied readiness: preserve the error, keep money movement paused, and repair Keychain access before retrying.

## Export the public identity record

```sh
node packages/adapters/bin/hookemon-wallet.mjs export-public --out /absolute/path/operations-wallets-public.json
```

The command accepts `[--service hookemon-operations] [--keychain-command /usr/bin/security]` when an explicit operations record uses a non-default Keychain location.

This command exports both public identities, not secret material:

```json
{
  "schema": "hookemon-operations-wallets-v1",
  "evm": {
    "address": "0x...",
    "keychain": {
      "service": "hookemon-operations",
      "account": "operator-evm"
    }
  },
  "solana": {
    "publicKey": "...",
    "keychain": {
      "service": "hookemon-operations",
      "account": "operator-solana"
    }
  },
  "generatedAt": "..."
}
```

Store the export in the owner-controlled operations record, outside the repository and outside environment files. It is a public identity record, not a backup of signing material. The coordinator copies this public record into `decisions/owner-inputs/launch-inputs-owner.json`; this CLI deliberately does not edit that file. Compare it with the configured onchain Operations address, policy allowlists, and deployment record before any funding or live use.

## Fund only after public binding is verified

Fund neither wallet until the exported public record is checked against the approved Operations binding and transaction policy.

- Send the chain-4663 native asset to the Operations EVM address for transaction gas.
- Send SOL to the Operations Solana public key for transaction fees, plus the Solana stablecoin pack budget needed for the cycle.

**OPEN FACT — funding amounts.** The exact EVM native-gas float, SOL fee float, stablecoin pack budget, source accounts, and cycle cap are owner decisions that the coordinator must record before any production funding. Until that record exists, use only `generate`, `show`, `probe`, and `export-public`.

## Recover native assets sent to the Operations address on the wrong chain

Use this owner-operated command only when native assets reached the Operations EVM address on EVM L1 instead of chain 4663. It reads the public Operations address from the Keychain child, quotes the native asset to the native asset with the same recipient, reads current fee data, reserves twice the 21,000-gas transfer cost before quoting, then estimates the returned transaction and requotes once if the final margin-adjusted reserve is larger. It refuses a non-positive amount or one below the Relay minimum. The default is a dry-run and exits with code 2 without signing or broadcasting.

```sh
node packages/adapters/bin/hookemon-bridge-native.mjs --from-chain 1 --to-chain 4663 --amount max --state-dir /absolute/path/to/operations-bridge-state
```

After reviewing the printed sender, recipient, value, gas limit, maximum fee, Relay request ID, expected destination amount, and expiry, use the exact same command with `--confirm`:

```sh
node packages/adapters/bin/hookemon-bridge-native.mjs --from-chain 1 --to-chain 4663 --amount max --state-dir /absolute/path/to/operations-bridge-state --confirm
```

`--confirm` still requires an interactive `y` before the Keychain child signs. The command accepts an origin-chain RPC override through `--rpc-url` or `HOOKEMON_ORIGIN_RPC_URL`; its destination RPC is the pinned chain-4663 binding. It follows Relay's documented [`POST /quote/v2`](https://docs.relay.link/references/api/get-quote-v2) request fields and its documented [status endpoint](https://docs.relay.link/references/api/api_guides/bridging-integration-guide). It refuses quotes with a different sender, recipient, chain, asset, amount, ERC-20 operation, or more than one executable step. Before broadcast it writes the request ID, signed-byte digest, and later transaction hash under `--state-dir`; a retry reuses persisted signed bytes instead of producing another signature. It polls Relay and the chain-4663 native balance until the expected credit arrives or the timeout expires. Do not run this command from the runner or use it for any other route.

## Backup and recovery

The CLI deliberately cannot export a wallet secret. A Keychain item is per Mac, so choose one of these honest recovery paths before funding:

1. Keep a current Time Machine or other encrypted whole-Mac backup that includes the login Keychain, and restore it only into the authorized Mac login.
2. If the Mac or its login Keychain is unavailable, generate replacement identities and rotate the public bindings. For the EVM identity, use the approved `setOperations` or emergency Operations-rotation path from the Phase 3 plan; update the Solana signer policy and any relevant allowlists before using the replacement.

Do not use `security export` as a wallet-backup workflow. It does not provide a safe, portable secret-export process for these bot keys.

Keep a separate, access-controlled record of the two public identities, their service/account labels, creation date, and the recovery procedure's owner. Test recovery in a non-production Keychain context: restore only through the approved operating-system process, run `show` and `probe`, and compare the public export with the recorded identities. The drill must not sign, broadcast, or fund a production account.

Never back up a seed, mnemonic, private key, or Keychain secret by placing it in an environment variable, `.env` file, text file, repository, CI secret dump, shell command, screenshot, chat, or cycle journal.

## Rotation and compromise response

For a planned rotation or suspected compromise:

1. Pause execution and process claims through the approved controls, and stop the runner from requesting signatures. If the Mac has died, begin the approved `setOperations` or emergency rotation instead of trying to recover an unverified Keychain item.
2. Preserve the cycle journal and reconcile every `PREPARED`, `SIGNED`, `BROADCAST`, `SENT_UNKNOWN`, or otherwise unresolved action. Do not create a replacement transaction, nonce, blockhash, or signature while an old request is unresolved.
3. Export and retain the old public identity record for audit. Rotate the onchain Operations authority, signer policy, allowlists, canaries, and funding destinations through their owner-approved paths before asking the replacement identity to move value.
4. Create the replacement deliberately:

   ```sh
   node packages/adapters/bin/hookemon-wallet.mjs generate --identity operations-evm --replace
   node packages/adapters/bin/hookemon-wallet.mjs generate --identity operations-solana --replace
   ```

5. Run `show` and `probe` for both identities, then write a new public export. Compare it with every updated public binding before resuming.
6. Disable the old identity according to the incident procedure only after recovery evidence, outstanding-action reconciliation, and the new binding have been confirmed. Do not delete the only recoverable record before those checks complete.

An EVM identity rotation changes the public address that is allowed to call the onchain Operations path; a Solana identity rotation changes the bot signer for the collector and return legs. Neither change is complete merely because a new Keychain item exists.

## OPEN FACT — production funding

**What is missing.** The final EVM and Solana public addresses, native-gas float amounts and sources, the cycle asset funding amount, policy caps, and owner authorization for production funding are not yet recorded. The public chain bindings and provider readiness evidence also remain prerequisites for a live money path.

**How to resolve it.** Generate both identities, export their public record, bind and verify the EVM Operations address and Solana account in the approved deployment/policy records, run the required readiness probes and canaries, then have the owner record the exact funding amounts and source-authority approval outside this repository.

**Closest verified alternative.** Use `generate`, `show`, `probe`, and `export-public` only, and run rehearsal or fixture flows with no production funding, signing, or broadcast.
